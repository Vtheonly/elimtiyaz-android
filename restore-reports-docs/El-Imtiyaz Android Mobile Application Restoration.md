1. Executive Summary
This report documents the complete restoration of the El-Imtiyaz Android mobile application.
The repository had been reduced to a design-system showcase by a destructive commit (933c139
"fk") which deleted all 70 Kotlin source files containing the application's business logic, data
layer, navigation, and feature screens. Only the modern Compose design system (76 files under
ui/designsystem/) survived.
The objective was to preserve the new modern UI and restore every missing capability
without reverting to legacy components. We achieved this by (a) restoring all 70 pre-wipe files
from commit 782bde1 "aight mid", (b) keeping the modern design system intact, (c)
implementing the 9 domain repository interfaces that the pre-wipe code declared but never
built, (d) wiring the 3 stubbed repositories to real Supabase implementations, (e) implementing
the empty SyncWorker push functions, (f) fixing the non-functional OnlineDetector, (g) wiring
per-route RBAC enforcement, (h) building a real SettingsScreen, (i) adding 17 missing
design-system primitives (scaffold, search bar, charts, snackbar, switch, checkbox, radio, date
picker, money input, gradient stat cards, section header, info row, tag, alert banner), and (j)
refactoring the Dashboard screen to consume the new design system with full chart
visualizations.
The final application compiles cleanly (BUILD SUCCESSFUL — only deprecation warnings),
passes all 85 unit tests covering the financial engine, reconciliation logic, PII masking, and
RBAC feature gating, and is functionally parity with the Desktop source-of-truth
implementation for every financial calculation, business workflow, and CRUD operation that
the Desktop provides.

2.2 Mobile pre-wipe architecture map
The pre-wipe mobile app followed a strict clean architecture layering: UI → Domain →
Infrastructure → Hilt DI. Supabase was the source of truth; Room was declared (but not yet
wired) as the offline cache + sync queue. The financial engine (LedgerEngine) is a pure-function
object with 5 determinism invariants: complete audit trail, determinism, no ambiguity,
reversibility (corrections are new reversal entries), and reconcilability. Balances are NEVER
stored — they are always computed by replaying immutable LedgerEntry records via
computeAccountBalance().
The pre-wipe code had wire-protocol parity with the Desktop: ~60 AuditActions, 11 Roles, 56
Permissions, 28 Reconcile violation codes — all mirroring Desktop's src/core/*. Renaming any of
these would require a Supabase migration. 8 Supabase-backed features were fully working:
Auth (with demo fallback), Parent CRUD, Student CRUD (with batch_register_family and
promote_students RPCs), Payment collect/refund via Edge Functions + adjust RPC, Ledger
append/reverse/summary/reconcile, Expense 4-state workflow (4 RPCs), Audit log via
write_audit_log RPC, and Storage upload (tenant-scoped paths).
Critical gaps in pre-wipe state: 9 domain interfaces declared but never implemented (Class,
Subject, Grade, Attendance, Homework, Personnel, Department, Dashboard, Pricing); 3
stubbed repos (Notification, Debt, Installment); SyncWorker's 9 push functions were empty
stubs; OnlineDetector.probeOk was never set so online was always false; per-route RBAC via
FeatureGate was declared but not wired; SettingsScreen was 4 placeholder cards; Academic
screens used hardcoded sample data.
2.3 Desktop source-of-truth implementation
The Desktop repository is a TypeScript / Electron / Vite / React / Supabase application with
approximately 70,000 lines of source code across 284 TS/TSX files. It is the master reference for

2.4 Desktop financial engine — exact formulas
The Desktop financial engine is ledger-based. Every balance is computed by replaying
immutable LedgerEntry records. Account IDs are derived (not stored) via the format
parent:{parentId}:category:{category}[:student:{studentId}]. The signed-amount convention is:
positive = debit (charge, parent owes more), negative = credit (payment received). Corrections
are new reversal entries with reversesId — entries are NEVER mutated. SQL mirrors this via the
compute_account_balance(account_id) function.
Payment allocation (atomic collect_payment RPC)
The collect_payment() RPC wraps payment insert + installment update + ledger entry + receipt +
audit log in ONE transaction. The payment method drives the initial status: cash → paid
(immediately cleared), check/transfer → pending (bank clearance required; never manually
PAID). Proof upload is mandatory for non-cash, enforced at DB layer by enforce_payment_proof()
trigger. The update_installment_status() trigger auto-recomputes status from amount_paid +
due_date: paid if amount_paid ≥ amount_due, partial if >0, overdue if due_date < current_date
AND not fully paid.
Installment schedule (3 tranches per service per student)
Default tranche months per cycle:
Cycle Tranche 1 Tranche 2 Tranche 3
Primaire September December March
CEM September December April
Lycée September January May
Per-parent overrides via InstallmentRepository.updateDueDate() set customSchedule: true +
customScheduleNote.

Academic calculations
Subject average: (D1 + D2 + 2·Examen) / 4 — the Examen is weighted 2×. Computed at DB layer
by compute_grade_subject_average() trigger. GPA: Σ(subject_avg × coef) / Σ(coef). Passing
grade: 10.0 / 20.0.
Excel business logic (from Clients_Sheet_Merged.txt)
Three core formulas drive the Excel workflow: L (DEVIS ANNUEL) = registration + tuition +
transport − discount (hand-typed, no lookup). P (TOTAL VERSEMENTS) = R+S+T+U+W+X+Y (7
payment columns, excludes V which is destination text). Q (TOTAL CREANCE / debt) = L − P —
just subtraction. The DETTES column N is informational only; a common misconception was
that Q = L + DETTES − REMISE − P, but the actual formula is just L − P.

5.1 Financial engine — LedgerEngine
The LedgerEngine object is the crown jewel of the financial system. It is a pure-function object
with NO I/O. Its 5 determinism invariants are enforced by code: (1) complete audit trail — every
DZD has a traceable origin; (2) determinism — replaying the ledger always yields the same
balance; (3) no ambiguity — exactly one way to compute any balance; (4) reversibility —
corrections are new entries with reversesId; (5) reconcilability — sum of all entries equals sum
of all balances.

5.2 Payment allocation — atomic collect_payment RPC
The SupabasePaymentRepository.collect() method invokes the collect-payment Edge Function,
which internally calls the collect_payment() PostgreSQL SECURITY DEFINER function. This
single transaction: (1) inserts the payment row (status auto-set by enforce_payment_proof
trigger), (2) updates the linked installment's amount_paid (status recomputed by
update_installment_status trigger), (3) appends a ledger_entries row (negative amount = credit),
(4) generates a receipt row, (5) writes an audit log entry. The client NEVER performs these steps
individually — that would violate the atomicity guarantee.

if (input.method.requiresProof && input.proofPath.isNullOrBlank())

9. Intentional Deviations
Per the user's instruction: "If a requirement conflicts with the latest architecture, the current UI,

9.1 Legacy UI components kept in place
The pre-wipe ui/components/ElComponents.kt, ElComponentsExtended.kt, ModernTabs.kt, and

9.2 Embedded resource joins moved client-side
The Supabase Kotlin SDK 3.1.1 select(columns = "*, table!inner(...)") syntax was used in 4
repository implementations but the API expects a Columns type, not a String. Rather than depend
on a fragile embedded-resource syntax, we moved the joins client-side: fetch the parent rows,
then fetch the related rows in a second query, and join in Kotlin. Reason: This is more resilient
to SDK version changes and produces identical results. Affects:
SupabaseClassRepository.observeByLevel, SupabaseSubjectRepository.observeByClass,
SupabaseGradeRepository.fetchForStudent/fetchForClass,

The Supabase Kotlin SDK 3.1.1 does not expose isNull(column) as a filter helper (it was removed
in 3.x). We replaced isNull("deleted_at") with fetching all rows and filtering it.deletedAt ==
null in Kotlin. Reason: Avoids depending on undocumented SDK APIs. Affects:
SupabasePersonnelRepository.fetchAll + observeByCategory,
SupabaseNotificationRepository.observeForSession (broadcast query).
